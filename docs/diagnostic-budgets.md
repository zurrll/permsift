# 模块与 worker 诊断预算

2026-10-05。node-module-load-v5 修复了 v4 的一个诊断盲区：模块事件先耗尽共享额度时，后来创建、unref 或终止的 worker 可能完全没有父侧线索。前次真实 lint 的事实仍见 [原观察可靠性记录](observation-reliability.md)；该轮没有重跑 execa，也没有执行它的安装或权限搜索。本文记录 v5 的分配；当前 v6 保留 worker 分配，并进一步[分离加载与解析额度](load-and-resolution-budgets.md)。

## 在原上限内分配

每个 Node 进程/线程仍最多 10,000 个事件、2,000,000 字节；读回最多 64 份日志、32 MB。默认分配如下，事件不包含 header/footer，字节计数只统计对应事件行：

| 用途 | 事件 | 字节 | 耗尽后的行为 |
| --- | ---: | ---: | --- |
| 模块解析/加载、子进程启动明细 | 9,872 | 1,927,808 | 停止明细，保留 event_limit / byte_limit / text_limit |
| worker 创建事实 | 最多 16 | 48,000 | 不再跟踪新 worker，记录遗漏数量与原因 |
| worker ref/unref、terminate 请求、父侧 exit 历史 | 112 | 16,000 | 停止追加历史，已跟踪 worker 的最终状态仍更新 |
| 最终 footer | 不计事件 | 8,192 | 保存两类统计、原因和至多 16 个最终状态；不能正常写完时保留采集缺口 |

worker 两行合计最多 128 个事件、64,000 字节。header 也受总字节上限约束，因此接近总字节上限时可用额度会稍少。小额内部测试上限按比例缩小预留；这不是新增的用户配置选项。16 指一份父日志累计跟踪的 worker 数，包括已经结束的 worker；不会通过删除旧状态无限扩展覆盖。

模块明细和 worker 历史各自停止，历史不能花掉创建额度。创建事件保留声明入口，但 footer 只保存线程身份、最后观察到的公开 API 引用状态、终止请求和父侧退出事实，不重复长入口。仍使用 interned-v1 字符串编号，完整路径、解析边和有效前缀可还原。

## 父侧状态能说明什么

trace_diagnostics.budget 是实际分配；channels 是已写入的事件/字节数、历史用量、遗漏 worker 数和耗尽原因。worker_states 来自有效的父 footer；缺父 footer 时不会补出这些字段。报告中的 worker_end.state_source = parent_footer 明确区分这份最终状态与普通历史行。

已跟踪 worker 的状态在构造、公开 ref/unref/terminate 调用和父侧 exit 回调中更新，即使历史额度已耗尽也继续更新。任务后注册的同步 process exit 回调可以再次更新 footer。引用状态从构造时的默认值及包装到的公开 ref/unref 调用得来，不声称覆盖 Node 内部每个 MessagePort 的变化；终止请求也不等于终止成功。没有观察到 worker exit 时只记录 parent_exit，没有猜一个退出码。

这不能替代 worker 自己的 footer。明细截断、历史截断、worker 遗漏、缺 footer 等问题仍保留 incomplete，不把“已解释原因”改成“采集完整”。没有被跟踪的 worker 不从相邻线程或任务成功推测原因。仍是可信任务的协作式观察，不是防篡改的安全监控。

## 有限反例与交付检查

[trace-budget.test.ts](../test/trace-budget.test.ts) 用 7 个小 Node 主任务覆盖：先耗尽明细事件/字节再创建 worker；大量 ref/unref 后在退出回调中 unref 或请求终止；超过可跟踪数量；长入口耗尽创建字节；自然结束后的 footer/保存报告损坏。主任务会创建小型 worker，数量上限案例本身创建 10 个；这不是只有 7 个进程/线程。每份实际日志核对总字节、事件和 footer 上限。损坏原始 footer 保留有效模块前缀，损坏的保存材料不能提升完整性。正常任务不因诊断额度耗尽而失败。

原 worker 异常、晚退出回调、字典截断与旧完整字符串日志反例继续保留。真实 macOS 沙箱中的 unref 案例同时核对任务和边界通过、观察不完整、父 footer 状态来源、原生执行材料与摘要一致。类型检查、完整单元/组件和观察/编译/打包集成作为本轮本地检查；全部 82 项集成及 Linux Node 22/24 留在 [默认 CI](ci-validation.md)。

本地最终完整单元/组件 285/285，测试进程 18.26 秒；真实 macOS 观察/编译/打包集成 17/17，测试进程 22.37 秒；类型检查通过。随后仅针对 CI runner 补充“父进程收到取消，但子命令正常返回 0”的反例，3 项 CI 分组/runner 测试仍通过，不重复运行项目任务。上述时间不含构建，也不合并开发中定向反例的多次运行；不是新旧性能对照。

这些测试证明预算隔离及诊断一致性，没有解决重型工具链的模块明细容量问题。后续用户提供的 v5 对照中，同一套 XO/ESLint 配置检查全项目和单文件都耗尽 9,872 个明细事件，已保存依赖模块、包实例和工作区解析边分别相同；父 footer 也已保留辅助 worker 的 unref 事实。见 [工具链事件压力](toolchain-event-pressure.md)。这类问题不能仅归于 execa 的项目规模；当前实例仍不完整，也不能推广为所有 XO 版本/配置必然触顶。
