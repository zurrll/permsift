# 实测后的修订计划：自然接入任务，解释未观测的依赖

2026-10-05。基于 v0.12 / `1ef872b` 制定；两次交付已完成，结果、局部缺口与成本见 [实测记录](real-task-results.md)。下面保留实施时的设计和验收依据。

这次先处理 execa 实测暴露的接入与解释问题。项目的长期定位继续保持开放，不按版本号增加功能。[原下一阶段计划](next-stage-plan.md) 中的 CI 分层暂缓，已有验证覆盖要求仍保留。

## 依据与判断变化

用户在主文件夹 `permstest/实验记录.md` 补充了第三个任务 tsd，结果保存在 `permstest/obs3/`。这份本机试用材料没有纳入源码仓库；下面记录核对过的事实和实施依据，不把本地绝对路径写成公共示例配置。

- 被测项目为 execa 10.0.1，已准备的依赖有 679 个安装实例、568 个包名；没有 package-lock，任务以离线方式运行。
- lint 记录 196 个实例，直接 tsc 记录 1 个，tsd 记录 108 个；lint 与 tsd 的加载包名交集为 40。
- 按安装路径对三任务各来源中的正向记录取并集，得到 287 个实例；392 个实例没有出现在已保存的来源记录中。这个差值不是未使用数量，来源不完整也会影响它。
- 直接 tsc 的 225 个输入文件归属 3 个包实例；其中 @types/node 有 83 个声明输入。tsd 没有编译输入来源，不能将 tsc 的覆盖推广到它。
- type-fest 的七个安装实例均没有加载或编译输入记录。抽查四个实例，发现 types 入口、声明文件与元数据，没有识别到 JavaScript 文件；父包来自多个工具链。增加 tsd 没有兑现“更多任务和镜头就能解释所有未记录包”的假设。
- 三个任务均通过，观察结果 incomplete。普通 node_modules/.cache 被当成未知依赖，影响清单、模块和编译归属；lint 另外存在 trace 截断/不一致和 worker 缺少结束记录的问题。
- 总时间约 66.73 秒，其中 task 阶段约 35.03 秒；其余约 31.70 秒包含冻结、克隆、清单核对、保存等。这不是与普通执行匹配的观察器开销对照，不能写成普遍开销比例。

本轮目标有两个：用户能自然声明原有任务；按包查询能将安装关系、包结构和本次执行记录一起解释。静态证据补充观察，不能替代观察，也不生成删除或撤权结论。

## 第一次交付：解除任务表达障碍，修正缺口分类

### 1. 明确声明退出码成功条件

首选新增一种无文件路径的断言，仍要求用户明确声明验收依据，例如：

```yaml
assertions:
  - type: exit_code
    value: 0
```

该接口已实现，并贯通既有模型和历史材料。首版只接受 0，与现有“命令正常完成且退出码为 0”的执行要求一致。保留至少一个明确成功条件，不把缺失 assertions 或空数组静默转换成退出码验收。

改动必须贯穿配置、任务定义/身份、执行结果、搜索、采用、check、只读解释及历史适配，不能只改 schema：

- 普通完成且退出码 0 才能满足该条件；非零退出、超时、中断或缺少进程结果不能通过。
- 成功条件与权限边界、安装核对、保护目标分别判断；新增条件不绕过这些要求。
- 文件检查仍检查本轮新产生的文件；产物刷新、保存与离线诊断只处理有文件目标的条件，不能把无路径条件当成文件。
- 报告说明本任务以退出码验收，检查强度取决于命令自身的检查；不将其描述为独立验证了业务正确性。
- 从文件/结构化结果检查改为退出码检查，属于验收约定变化。旧采用记录不能因此自动成为当前保证。
- 旧配置、原有成功材料和失败/未知材料继续按原语义解释。

### 2. 原命令与采集器范围分别表达

原样执行 `npm run lint` 和 `npm run type`；后者保留项目声明的 `tsd && tsc`，不拆成一个 tsc 后冒充完整任务。不再为验收制造 lint JSON、tsbuildinfo 或 tsd 成功标记文件。

模块观察沿用已有预加载机制。编译输入仍只支持明确配置的直接 tsc；普通 npm script 没有此来源时显示未采集。明确请求了当前不支持的编译采集方式，继续给出具体说明，不静默忽略声明或伪装为空输入。直接 tsc 可以作为独立诊断任务，不能代替原 type 任务的验收。

本轮不解析任意 shell 命令、不劫持嵌套编译器，也不新增 tsd 编译采集器。

### 3. 修正普通缓存的分类及影响范围

识别 node_modules/.cache 这类已确认的普通辅助目录，记录忽略范围，不将其作为漏掉一个包的证据。不能一概忽略所有异常条目；未识别包、符号链接、元数据错误和扫描上限仍保留真实缺口。

检查清单问题传播：安装清单范围、原始模块采集、编译输出采集和包归属完整性分别表述。影响归属的真实缺口仍保留，普通缓存分类错误不再使其他来源一起变为 incomplete。

### 4. 为已出现的 trace 问题留下可诊断事实

区分事件/字节上限、文本截断、写入错误、记录计数不一致和缺少结束记录。保留实际计数、对应上限及进程/线程结束状态，控制保存体积。

已有材料没有这些细节时说明未保存，不倒填原因。新增诊断后再判断 lint 是容量问题还是 worker 生命周期问题；只有定位后才调整相关实现。缺少结束记录不自动当成成功，增加上限也不能替代定位。

退出码继续保留 0/1/2 的既有语义。任务通过与采集不完整清楚并列，严格程度选项暂不增加。

### 完成条件

原任务不需要假产物便能表达；非零/未知过程不能接受；真实边界要求保持；缓存问题不会制造虚假缺口；新 trace 问题有具体原因字段或明确的未保存说明。完成这一交付即可继续试用，不等待下一项全部完成。

## 第二次交付：按包解释安装关系、结构和任务记录

扩展现有 `inspect --package`，先回答两个具体问题：

1. type-fest 七个版本分别由谁引入，安装内容和声明入口有什么特点，哪些任务/来源有记录或缺口？
2. eslint-visitor-keys 三个版本分别有哪些安装父依赖，以及本次实际解析/加载来自哪里？

### 1. 保存有范围说明的安装依赖关系

从任务执行前同一份已准备依赖中的 package.json 声明和实际安装布局建立关系。按安装实例定位，保留声明种类、范围和目标路径；根项目声明与包之间声明分别保存。

首版提供直接父依赖以及有限的根项目引入路径，限定节点、边、深度和展示路径数量。嵌套重复版本、循环、可选/peer 缺失、不可确定的定位须准确表达；不能按包名连接所有同名实例。它描述声明与安装布局中的关系，不是实际加载链，不证明每个父包本轮使用了这个依赖。

复用当前受支持的 npm 目录布局；不以执行 npm ls 作为生产采集方式，不运行项目脚本或联网。不扩展其他包管理器、workspace 链接等安装结构。

### 2. 保存有边界的包结构摘要

保存 types/typings、main/bin/exports 等相关入口声明和文件结构摘要，优先复用已有文件清单，避免每个任务另外完整遍历依赖树。未能复用时先测量额外扫描成本，保持范围有界，并分别记录摘要完整性。

统计声明文件、常见 JavaScript 代码文件及其他内容。不能只数 .js：.mjs/.cjs、非声明的 TypeScript、原生模块、Wasm、无扩展名入口及资源文件都会影响解释。入口声明还需区分是否有相应文件证据；条件入口不能靠选取一个字符串假装解析完整。

首版展示可核对的事实，例如“声明 types 入口；本次结构清单含若干声明文件，未发现已识别的常见运行时代码文件”。可以说明这些结构与普通 Node 加载视角未见记录相容，但不能因此证明没有运行时作用、可以删除或本任务绝不会读取该包。

### 3. 三类证据在一个查询中各自可见

- **安装关系**：谁声明/引入了这个安装实例？
- **结构证据**：发布到当前安装中的入口和文件是什么？
- **执行记录**：各任务的模块、编译和构建来源记录了什么，来源是否完整？

用来源和证据支持解释，不新增“类型专用/工具专用/无用”的全局分类，也不为每个未记录包编造一个确定原因。

这些摘要在新记录生成时保存到有版本与输入身份的材料中。离线查询只读取经过校验的保存材料，不读取当前项目去补历史事实，不执行任务。旧报告没有关系或结构资料时仍能查看已有记录，明确显示未保存；不拿 terminal/summary 缓存充当原始依据。

### 完成条件

两个目标查询能独立解释安装实例、结构与执行记录的区别，并指出缺口；脱离项目仍可读取新材料。混合内容、非 .js 代码、扫描不完整及未知依赖定位等反例不会被误判为纯类型或无用。若这些查询仍只重复用户已经知道的数字，应先修解释，不增加更多采集器。

## 验证安排与成本

开发验证使用有限的固定反例，集中检查改变的语义：

- 退出码成功、非零失败、超时/缺过程未知、退出码与文件条件共同验收，以及采用后的验收约定变化。
- 缓存可忽略与真实未知包不能忽略；真实 trace 截断/错误/缺结束记录分别呈现，旧材料原因缺失不倒填。
- 嵌套版本与父依赖定位、循环/可选/peer 缺失，以及声明内容、混合代码、非 .js 内容和不完整扫描。
- 历史记录可读，新资料脱离项目可查，材料损坏或身份/引用不一致不能成为确定解释。

现有完整单元/组件检查以及相关 macOS 集成按改动范围执行，实际结果和成本另记。成功次数不作为用户价值证据；已通过且未再改变的真实场景不重复跑。

真实 execa 验收默认保持现有已安装输入，不新增安装或权限搜索。先普通执行原 lint/type 各一次确认基线，再观察各一次；正常情况下共 4 次项目命令执行。普通与观察的命令、输入和缓存条件分别记录，不能把只执行一次的差值泛化为稳定开销。最终验收尽量合并两次交付的核对；第一次交付若需先验证，可以先跑，后续只补改变的部分。

首次失败/未知后保存材料并分析，不自动反复重跑。若新的 trace 原因仍需要核对，最多增加一次定向 lint 观察，再根据证据决定是否需要另立问题。固定夹具及既有集成内部执行成本与这四次真实项目命令分别列出。

直接 tsc 的现有记录可复用；仅为新编译事实补一轮时记录其独立命令与额外成本。读旧报告和离线查包无需新任务或安装。与 npm ls 的安装关系、原始 package.json、包文件清单及既有加载边核对答案，不用新展示自身作为唯一标准答案。

unit/ava 是可选的后续探索，不作为上述两次交付的必需验收。先核对原任务的网络、平台、时间和临时文件要求；coverage 文件存在不能独自证明单元测试完成，也不证明退出码问题在多个项目普遍成立。不能为了接入修改上游测试或自动扩权。

## 本轮收口与暂缓项

后续观察可靠性改动和唯一一次定向 lint 已完成，结果见 [观察可靠性记录](observation-reliability.md)。字节预算压力已降低，事件截断和未保存的 worker 父侧事实仍有缺口；不能把这次交付写成真实 lint 已完整采集。

交付为任务成功条件、缓存/trace 诊断修正、按包解释视图、对应测试与说明，以及一次有实际成本的 execa 接入记录。工程正确性与用户是否能独立理解、是否据此采取行动分别记录。

优先检验用户能否少做手工步骤，回答“谁引入这个版本、它包含什么、哪些任务留下证据”；人工时间没有测量就不报告省时。没有升级/删除/配置决定也保留为结果，不为了证明价值制造维护改动。

CI 分层、任意 npm 安装、新编译采集器、自动删除建议、观察驱动撤权、全包用途分类、可视化、跨次缓存和新沙箱后端继续暂缓。长期定位在这些真实使用反馈之后再讨论。
