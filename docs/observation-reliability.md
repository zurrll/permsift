# 模块观察可靠性：重复日志与 worker 缺口

2026-10-05，延续 [原任务实测](real-task-results.md)。这一轮实现了更紧凑的记录和父侧 worker 诊断；一次 execa lint 证明字节压力降低，但没有证明该任务已能完整采集。它仍有事件截断和缺 worker footer 两类缺口。

## 改了什么

node-module-load-v4 的 interned-v1 在每份日志内复用模块 URL、父模块和请求字符串。第一次使用时随事件定义字符串，之后引用编号；resolve/load 的去重键也改为编号组合。没有压成包名汇总，读回后的模块路径、解析关系与包归属保持原有语义。字典最多 30,000 项，文本仍最多 4,096 字符。

每进程/线程的 10,000 事件和 2,000,000 字节预算未提高。字典定义不另占事件；worker 动作也计入同一预算，不优先于模块事件。读回保留有效前缀，拒绝未定义编号、重复定义、未知编码或损坏记录。旧完整字符串日志及没有新字段的 usage.json 仍可读。

包装 Node Worker 构造及 ref/unref/terminate，记录创建线程、声明入口、引用状态变化、终止请求和父侧 exit 回调。父进程同步退出阶段记录尚未观察到退出的 worker 状态。记录能关联到 worker 日志时，在 trace_diagnostics.worker_end 中保留父线程证据和解释；父侧退出 0 也不能替代 worker footer。没有父侧事实时保留未知原因。

未增加 error 监听，因此任务原本未处理的 worker 异常仍会失败；没有保存 eval 内容、workerData 或完整参数。构造器、方法包装和监听可能影响行为及时序；任务也能绕过或修改它们。这是可信任务的协作式观察，不是防篡改监控。

任务自己的同步 exit 回调可能在观察器的退出回调之后继续加载模块、调用 terminate 或 ref/unref。现在这些事件会写在最终 footer 之前，并刷新相应父侧退出状态；不会先写“完整结束”再丢掉这部分同步工作。异步工作、强制终止、信号退出的遗漏不会因此被补齐。

## 小案例先验证什么

先用旧观察器运行三个很小的 Node 进程：自然结束、主动 terminate、unref 后随父进程退出。三个父进程均退出 0，只有自然结束的 worker 留下 footer。这个结果解释了为什么“主任务通过”不足以把 worker 记录判成完整。

[Node terminate 文档](https://nodejs.org/docs/latest-v24.x/api/worker_threads.html#workerterminate)说明它会停止 worker 的 JavaScript 执行；[unref 文档](https://nodejs.org/docs/latest-v24.x/api/worker_threads.html#workerunref)说明该 worker 不再独自保持进程运行；[process exit 文档](https://nodejs.org/docs/latest-v24.x/api/process.html#event-exit)限定退出监听中的同步工作。这些机制资料与本机反例共同支持实现，不能替代真实任务的结束证据。

重复路径夹具包含 180 个模块，共 364 个事件。紧凑日志为 87,527 字节，同一组事件还原成完整字符串表示为 167,775 字节，减少约 47.8%。两份表示读回后的加载模块、解析边、包记录、进程、事件数和状态逐项一致。这是同一事件流的编码比较，不是两次真实 lint 的性能基准，也不保证其他项目有相同比例。

其他固定反例验证了自然退出、terminate、unref、重复 ref/unref、较晚的同步退出回调、ESM Worker、继承与子类、未处理/已处理错误、不继承 preload 的 worker，以及损坏/截断字典。最终另补了一个“父侧先耗尽预算，再创建 worker”的反例：即使夹具知道它调用了 unref，报告没有保存父侧事实，就仍不能输出 unref 的确定解释。

## 交付与未解决的收益问题

完整单元/组件最终 278 项通过，约 17.03 秒；相关 macOS 集成 17 项通过，约 23.14 秒，涵盖模块、编译、构建来源和新 unref 案例。开发中执行了三次完整单元回归，其中一次因新增夹具试图覆写只读 preload 失败，修正夹具后通过；固定小案例与这些测试内部的执行不计入上面那一次 execa 命令。没有重跑全部联网安装演示。

已验证的收益是：同一事件流占用更少日志字节；有父侧事实的 worker 缺口能区分并离线保留；同步退出回调不会在完整 footer 之后悄悄漏记。真实 lint 的缺口类别数并未减少到零，父侧诊断尚未在这一真实案例留下足够证据。人工理解时间、升级/删除决定和整体提速均未测量。

若继续处理这个案例，应先设计同一总预算中的关键事实保留方式，例如给少量生命周期事实留出有界份额，并明确这会减少可保留的模块明细。先用预算耗尽夹具验证，再决定是否值得另一次真实任务。这里没有实施预算分配，也没有简单提高事件上限、合并掉解析边或用父侧退出伪造 worker 的完整记录。
