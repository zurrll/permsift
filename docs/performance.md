# 耗时与中等规模项目实测

v0.7 把成本记录进实验报告，并用固定上游项目验证安装、编译、单元测试和构建 API。计时只描述实际工作，不改变任务 verdict、搜索预算或权限证据。

## 如何运行

```sh
npm run medium:prepare
npm run medium:verify
```

第一条下载 fast-glob 的固定提交 `48687898dd26d4e935a0e5ecf6720e7c5aeac15d`（3.3.3），核对原始受 Git 管理的文件，再放入已提交的锁文件和 verify.cjs。它不执行 npm 安装。第二条在真实 macOS 沙箱中冷安装验证三次，从其中一轮完整缓存构造固定种子，再做暖缓存搜索及导出规则完整重放三次。原始项目保持无 node_modules。

上游与适配范围：

- [fast-glob 源码](https://github.com/mrmlnc/fast-glob/tree/48687898dd26d4e935a0e5ecf6720e7c5aeac15d)，保留源码、测试、fixtures、tsconfig 和 MIT 许可证。
- 上游没有锁文件，且 .npmrc 内容为 `package-lock=false`。示例提交生成后的 v3 锁文件，共 507 个依赖项；实验排除这份 .npmrc，使用显式注册表和锁文件。未来不重新解析版本范围。
- 上游固定 Node 14 类型，而当前解析出的 glob/minipass 声明使用更新的 EventEmitter 类型。编译脚本明确使用 `--skipLibCheck`，跳过依赖 .d.ts 检查，仍检查上游 src 并产生 JavaScript 和声明产物。这不是无改动的原始 npm run build。
- 运行全部 `out/**/*.spec.js` 单元测试，要求精确 246 项、246 通过、零失败、零跳过；不包含上游 .e2e.js、lint 或 benchmark。
- 额外验证编译后的同步/异步 API 在原始 fixtures 中返回同样的 9 个 Markdown 文件，并检查新声明产物。缺报告、编译/测试命令失败或旧产物均不能通过。
- npm ci 固定禁用生命周期脚本。本例能完成这些任务，不意味着任何有原生构建、下载脚本或私有依赖的项目均可用。

## 计时口径

v0.8 在原分项之外增加 hash_scan 根扫描诊断，有界并行保持原内容摘要与源/副本两次核对。service time 会重叠，不能与独占分项相加；微基准、重装一致性与同时间预算对照见 [完整校验说明](hash-validation.md)。

report.json 的 timings、trials[].timings，以及证据的 summary.timings 使用单调时钟。phases 含 duration_ms 和 calls；不同类别统计独占墙钟时间，嵌套子操作不重复计入父项。并行根目录清单统计在同一个跨度内，调用数代表一次三根目录扫描批次；安装快照 hash 的一次调用也覆盖三根。CLI 同时显示总时间与耗时最多的一项，tighten 显示 search_complete。

| 类别 | 包含的工作 |
| --- | --- |
| freeze | 初始输入逐字节冻结及内容哈希 |
| clone | 输入、安装状态和暖缓存种子的独立克隆 |
| hash | 已冻结输入复核，以及安装快照源/克隆的内容、文件/目录模式、内部链接核对 |
| manifest | 工作区、缓存、临时目录的文件变化清单和暖缓存种子清单；包含读取文件内容 |
| preparation | 安装输入检查、npm 版本、目录准备、输出刷新、读取夹具和读目标类型核对 |
| probes | 实際前后边界探针及宿主对照，含沙箱启动与退出 |
| install / task | 对应命令及其后端启动/退出；安装还包括锁文件、清单未变检查 |
| assertions / discovery | 新产物断言、有界读写候选枚举 |
| reporting / cleanup | 证据和阶段报告写入、各轮副本及实验末尾输入/快照删除 |

total_ms 是本次测量范围内的墙钟时间，measured_ms 是类别相加，other_ms 是未插桩的编排、诊断等差额。实验计时从进入执行器开始，包括加载配置和初始文件准备。每轮的计时在写入自身证据前结束；其证据写入计入实验 reporting，随后副本删除计入实验 cleanup。实验计时截止最终报告写入开始，最后那次写入不包含在报告自身计时内。保留工作区时不执行该实验的 cleanup。一次最终快照下 total_ms ≈ measured_ms + other_ms；这些数不是 CPU 时间、磁盘物理读写量或 clonefile 共享块证明。

## 依据测量做的优化

此前，复用已安装状态的任务试验仍生成四轮完整清单：所谓安装前、安装后、任务前、任务后。实际没有运行安装，前两份既不用来决定安装规则，也不参与任务写入差异。

现在任务试验只生成任务前后的两份清单；`install_file_changes` 在没有安装时不再输出。任务前清单仍在准备、前置探针后实际读取，任务后清单仍从实际文件生成，不从缓存推断任务是否写入。成功完成两段的完整安装试验保留四份清单。

冻结源与克隆的完整性核对、每轮边界探针、拒绝后的恢复复测、最终从原始输入重新安装验收均保持。优化只消除两个不存在阶段的变化扫描，不减少完整性校验。

实测还发现所有轮次的目录都留到末尾会积累百万级文件条目。默认在证据安全写入后删除本轮目录，只保留下一轮所需的原始冻结输入和独立安装快照；保留工作区参数继续保留所有轮次。源码试验的删除不删除安装快照，后续候选仍核对并使用该快照。清理失败中止实验并标记 incomplete，不导出推荐规则。

## 同条件比较

```sh
# 第一次输出 .../summary.json，保留该目录中的固定种子与配置
npm run medium:verify
# 修改扫描实现后，使用同一输入/缓存种子/limits 对照
npm run medium:verify -- --baseline .permsift/fast-glob-profile-XXXXXX/summary.json
```

对照会核对冻结输入、配置、limits、平台、架构、Node/npm/后端版本、每轮阶段/权限/结论、最终四类规则和搜索完成状态。工具版本可变化；变化目标正是工具实现。任何核对不一致都失败，仍保留 comparison.json 供排查。后一轮还用 check 完整新安装复验旧规则三次。恢复与重放不算作候选；重放、check 的耗时与搜索分开。

这是单台机器的顺序观察，受文件系统缓存、网络、温度和后台负载影响。可以核对减少的扫描次数与同样的规则/结论，不能把单次总耗时百分比当成所有项目的速度保证。记录结果见 [validation.md](validation.md)。

## 实际配置成本和范围

本例需要一份任务 YAML、独立 limits、固定锁文件和约 30 行适配脚本。任务脚本串联上游编译/测试，提供稳定的测试数量及产物断言；不是“给任意项目自动猜出成功条件”。初始安装与任务各有两类手工收缩候选，项目读取候选由工具生成。没有量出人工配置分钟数，因此不报告虚构的配置效率提升。

每条策略至多 32 个授权，完整目录替换也不能超过 32 个孩子；本项目 node_modules 包数超过这一限制，并含 .bin 链接。因此默认结构候选无法把整个 node_modules 展开为所有包，报告仍可能保留这个读取范围。truncated 描述枚举/表达范围限制，search_complete 只说明已生成/配置操作是否试完。verified 说明最终规则在本次完整任务上通过，不说明每个包的读取均已做到最小。

本轮候选上限 40、时间上限 1800 秒，所有保留授权、拒绝与恢复证据及预算停止原因均写入报告。后续改善应根据这些实际摩擦排序，例如依赖读取规则的表达范围、完整性扫描成本或大树副本清理；本例没有顺带扩张安装脚本、包管理器或平台能力。

实测中，固定暖缓存的完整新安装与快照任务有不同的成本：大树克隆/校验可能超过 npm 从本地缓存重新安装的时间。不要把复用次数当作时间收益；当前保留同一安装状态的比较语义，下一步可单独评估执行策略及哈希成本。实际数字见 [validation.md](validation.md)。
