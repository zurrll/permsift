# 收益与范围的取舍

2026-10-02，v0.9 / v0.10 的设计与验收依据。

## 已兑现与仍待验证的收益

这是开源学习项目。快照、后端、探针、恢复和历史兼容带来的工程/学习收益已实现，但不能由此推导每个用户都值得运行完整权限搜索。

写权限从整个工作区缩到产物目录、安装/任务分阶段、任务断网，都直接减少给任务的修改/联网范围；check 让现有规则的日常复验不必重做搜索。这些效果已经在项目案例中验证，仍不是恶意任务无逃逸或风险降低百分比的证明。

公开依赖逐包读取的额外收益取决于威胁与输入：限制私有代码、敏感配置可能有价值，减少几个普通公开包的可读范围未必值得几十轮构建。不能把所有包当成同等敏感目标，也不能只按规则条数衡量安全效果。

v0.8 同候选观察省约 3.8 分钟；同 300 秒预算只多完成一个候选，最终权限没更小。优化实现有效，但更多搜索是否能产生值得的结果仍待验证。还没有外部用户采用、人工配置分钟数或实际风险降低数据。

## 两种测试成本

开发测试降低实现错误、误判、扩权和回归的风险；通过数量不是用户收益。真实任务搜索每一次完整执行都会由用户支付时间，须针对有价值的范围选择实验，而不是为了穷尽候选继续运行。

对于已经决定尝试的权限变化，保留任务断言、边界和恢复核对。减少成本优先控制“选择哪些问题”，不能把观察到的加载直接当成必要权限或安全撤销清单。

## v0.9 的价值假设

用户希望理解庞大的依赖集合：某任务观察到了什么、间接关系从哪里出现、升级后实际加载怎么变化。模块观察通过一次或少量任务运行获得线索，不需对全部包逐项撤销。

首版仅实现 npm 实际安装清单、Node 模块加载、受控子进程覆盖信息、可读/JSON 报告及基本前后对比。TypeScript 文件与 bundle 内容采集、自动候选、规则上限扩张、删依赖建议和其他包管理器延后。接口保留来源、范围和输入/环境身份，方便以后独立增加采集器。

已有依赖分析工具提供未用依赖或 bundle 分析；Permsift 需要证明绑定真实任务、沙箱与记录条件的动态证据能帮助具体判断。只有“加载了 N 个包”的总数不足以支持继续扩展。

## 验收与下一步门槛

1. 固定夹具正确区分直接/间接、未加载、作用域、嵌套重复版本，并解释观察关系。
2. 真实任务断言保持；fast-glob 区分编译与测试所涉及的模块，bundle-kit 直接演示原生进程盲区。
3. 受控代码/元数据改动能在对比中显示新增加载和版本变化；未知、失败和缺日志不会产生确定未使用结论。
4. 实测普通与观察执行的成本，分开列安装/准备总成本与任务成本。重复观察用于固定案例稳定性检查，不追求所有真实任务列表永久相同。

若无法解释来源，覆盖缺口让关键任务没有可用信息，或开销不符合用户需求，优先调整/缩小报告范围，不继续扩张搜索。观察驱动权限候选只有在完整输入覆盖及少量真实验证确有收益后才进入下一版；“45 个加载包等于一次验证”目前只是未成立的假设。

## v0.10：先修已知的编译盲区

调整先接 esbuild 的顺序：现有 bundle-kit 只包含构建工具，没有应用依赖可供产物归因验收。先让现有 fast-glob 编译任务解释类型文件等输入，并在摘要旁修正“506 个未观察包”容易被读成“未用”的表达。起手依据是明确的覆盖问题及已有真实任务，不是 507 个包或 246 项测试这些数量本身。

增加来源的价值假设是帮助用户判断“某包为何涉及本次任务、代码/配置改动后怎样变化”。模块加载和编译输入按任务、版本及运行条件关联，保留各自健康度与范围；同一包可以同时出现，不自动判成工具专用、应用专用或必要权限。数据源汇到一张表本身也不构成采用收益。

fast-glob 的 TypeScript 4.9.5 实测从 216 个解释文件识别 25 个输入包实例，包含 11 个 @types；可解释 @types/micromatch 从 src/utils/pattern.ts 引入。受控夹具 import type 改到另一个包，JS 加载列不变、编译输入列变化，ambient 声明包版本变化被单独识别。学习/诊断能力得到验证；没有外部用户人工时间数据，也没有将观察用于减少权限试验的证据。

## v0.11：用一次真实升级检验产物解释

受控样例验证模块来源与产物来源不同：esbuild 工具与运行外置包有 Node 加载记录，应用间接包和动态分块由元数据解释。纯转发包可以是输入而贡献 0 字节；不把它改叫“无用”。纯类型包不进入该次打包记录，也不能据此删除它。

真实样例复用固定 fast-glob 上游源码及夹具，加显式 TypeScript CommonJS 语法转换/esbuild 构建任务和最小锁定依赖；不是原先 507 个开发包任务或上游完整构建。观察能沿入口 → utils/pattern → glob-parent → is-glob → is-extglob 解释间接来源。glob-parent 5.1.2 → 6.0.2 后，工具加载集合不变，打包贡献从 934 到 1560 字节、JS 与 map 输出变化；三个 API 仍匹配固定 9 个文件。这给出一个具体可检查的升级影响，使用者可继续审阅对应版本改动，不能从体积推断风险或升级原因。

esbuild 自带 analyze 已能解释引入路径和体积。Permsift 的这次工程验收是把版本、产物变化、任务结果、观察条件和来源差异放在可比较报告中，而不是证明原有分析不够用。默认 observe 一任务一次，前后各一次；开发验收额外做普通对照，不把它算作用户必须支付的权限实验。冷安装网络耗时仍可能主导总时间，单次任务对照不能外推普遍开销。

已证明这些案例可被解释，尚未证明外部采用收益、节省的人工分钟或自动候选价值。下一步应让实际用户用报告解决自己的变化问题，再按缺口做扩展；没有必要为了更多统计继续逐包撤读或增加采集来源。

后续比较对象还包括 bundle 可视化和组件清单工具，不能只用未用依赖分析工具作参照。字节贡献不能作为必要性或敏感内容检测；执行阶段读取私有输入同样有安全意义，external 也不能直接决定构建阶段读权限。

## v0.12：已有事实的检索与离线比较

单任务已经有关联来源表和引入链，因此不把“重新拼装单任务”当成新的解释收益。实际阅读卡点在跨任务定位及两份已有报告没有独立 CLI 比较入口。inspect 按包名集中显示全部安装实例；compare 与 observe --baseline 共用比较逻辑，查询/比较不付新的安装或任务执行成本。工程回放验证输入不变和确切事实，没有由此报告人工时间节省。

另用固定 glob-parent 新版上游测试接入，源码及 package.json 不变，追加结构化 reporter；配置和 limits 分别 82 / 17 行。Mocha 升级只在测试任务产生已加载版本变化，API 模块记录稳定；两次实际报告均读回 20 项通过测试。旧版 nyc 内嵌依赖在安装预检被拒绝，暴露兼容门槛；没有通过改工具或扩安装能力掩盖。冷安装仍主导观察成本，离线便利不能代替新记录的生成成本。细节见 [使用检验](offline-pilot.md)。

兑现的是可集中找到已记录的实例、可重用保存的比较证据。仍未兑现外部采用、人工分钟或减少权限试验；下一步按真实使用问题收敛，不因增加入口继续扩张采集来源或权限搜索粒度。

## 第四轮：指定保护目标的收益与成本

用户现在可以挑少数需要保护的资源：正常任务完成、指定路径的直接操作仍被拒绝；任务改动需要访问保护目标时，结果分别显示任务失败和保护通过，自动修复不能撤掉约定。这是已验证的行为收益，不是量化安全风险下降或外部用户收益。

成本是通常每个 trial 增加两次批量沙箱检查。夹具只重现路径/类型和少量假文件，避免复制依赖树；报告单列 protections 时间。有/无目标的小示例记录真实耗时，没有把一个样本当作性能基准。已被保护禁止覆盖的授权删除，不再算权限范围收缩；目标数量和规则条数都不能代替收益判断。具体范围、成本及复现见 [保护目标](protection-goals.md)。

## 第五轮：让实验成果能用于维护

明确采用保存选择、理由、前序基线和最终验证证据；采用及查看不执行任务或安装，后续 check 继续真实复验。约定变化与本次通过分开表达，旧成功不会自动续成当前保证。小项目检验多次采用、源码变化、修复、删检查/保护目标、源报告清理和存储移动；大型项目检验复用成果的实际成本。

本机 fast-glob 507 包案例复用既有 70 次试验、约 939.8 秒搜索的完整最终基线。采用定向读取 3 次最终验证，只保留 5 个 JSON 文件、11,487,458 字节，耗时约 0.68 秒，无任务或安装。当前 check 用 3 次全新安装和任务完成原编译/测试/产物检查，0 候选，约 38.2 秒，输入摘要相同。历史搜索与本次复验的版本/环境和时间不同，不是同条件性能比较，不报告普遍节省比例。

实际发现原只读解释器会先读取全部搜索 sidecar，超过 128 MB 后最终证据未被加载。采用现在选择性读取完整最终验证，保持读取预算和检查纪律；不靠提高预算或忽略未知来接受基线。工程流程得到验证，几个月的维护收益、实际人工分钟及独立使用者能否理解保证范围仍未验证。

## 第五轮后的取舍：先解除已知接入障碍

成功条件诊断仍值得小范围验证，但现有安装预检已挡住真实 glob-parent 5.1.2 项目。优先支持父 tarball 中的内嵌依赖，让权限和观察两条路径都能使用原任务。没有合并打开生命周期脚本，也没有借机增加逐包搜索。

原 137 个内嵌实例现在可以确认父包归属，真实安装后核对名称/版本和父包声明。已发现 npm ci 的成功退出不能独自保证这些包实际存在，因此核对失败独立阻止任务及方案接受。原上游 16 项测试、138 项安装核对和依赖观察均通过；真实示例只运行一轮观察，0 候选。第一次试用发现临时目录权限不足，最终在示例中明确加入已有可信上限允许的 `@tmp`。源码和原命令保持不变。

兑现的收益是这个具体项目能接入并留下真实模块记录。最终冷安装仍占全流程大部分时间，不声称普遍提速、减少人工分钟或覆盖全部 npm 布局。保存检查和离线读回不增加安装次数；下一项成功条件诊断应继续以可行动建议的收益决定范围。实现与失败/成功成本见 [内嵌依赖](bundled-dependencies.md) 和 [验证记录](validation.md)。
