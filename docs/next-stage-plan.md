## A：整理验证成本与 CI

### 交付

1. 一份验证覆盖清单：每个当前 CI 步骤检查什么、使用公共 CLI 还是内部接口、是否有独有反例、是否需要公开项目下载/安装、已有耗时和保存材料。独有检查迁移后仍有明确入口。
2. 调整默认 CI，提供单独的手动场景验证工作流；保留现有 medium 手动工作流。
3. 一份开发验证说明及改动选择规则，显示本次实际跑了哪些层，不把未执行的层写成通过。
4. 一份调整前后收据：提交、环境、作业/步骤时间、结果及计数依据。失败、取消和超时一起保留。

### 第一版分层

| 层 | 触发与内容 | 验证目的 |
| --- | --- | --- |
| 快速检查 | 每次 push/PR：保留 Linux Node 22/24 的单元、类型和已有离线入口验证 | 解释、格式、身份、旧材料、参数和不同 Node 环境 |
| 真实沙箱回归 | 执行代码、测试、配置/夹具、依赖、脚本或 CI 改动：macOS 单元与完整集成套件；最小公共 CLI 流程 | 保持真实拒绝、恢复、保护、安装、保存与清理行为 |
| 扩展场景 | 手动选择；发行前按变更范围执行适用场景 | 公开项目准备、冷联网安装、长搜索、完整示例和接入复现 |

第一版只为明确的文档变更省去 macOS 执行；代码改动仍保留完整集成套件。先移走反复执行的扩展场景，暂不建立按几十个模块挑选集成用例的复杂映射。后续若完整集成成本本身成为阻碍，再凭覆盖证据细分。

最小公共 CLI 流程优先复用 doctor 和 bundled:verify 的默认本地注册表模式，覆盖环境检查以及 run/adopt/check/observe；计划额外成本为 1 次 doctor、3 次项目任务/安装、0 搜索，完整集成的实际成本另列。覆盖清单确认后才决定保留或替换其他小型入口检验。正常工具 npm ci 的联网与项目注册表实验分别记录，不能把默认回归描述为完全离线。

扩展场景保留原项目、命令、断言与实验条件，不为缩短 CI 偷改 repetitions 或减少一致性检查。将公开联网/安装长流程从默认串联链上移出，不删除其验证能力。外部维护、干净试用包和中等项目已有手动入口，按其原范围继续使用。

### 选择规则与验收

- 文档白名单仅限确认不影响执行的 README、docs 文本等。源码、package/lock、examples 配置/材料、test、scripts 和 workflows 改动默认跑真实回归；未知文件、无法确定比较起点或分类异常也跑真实回归。
- 检查一次 push 的全部改动和 PR 相对基线的全部改动；删除、重命名、混合改动、首次提交/无可用基线不能漏掉代码变化。
- 路由规则用有限的改动清单反例验证。不得靠改动文件扩展名或 PR 标题推断测试可以省略。
- 保留固定、可理解的作业状态；若仓库设置了必需状态检查，调整时核对其名称和依赖。文档任务的跳过范围明确可见。
- 关键实现故障仍使 CI 失败；保存日志/收据不能覆盖原退出状态。失败不自动反复重试，公开网络异常与实现断言失败分别记录。
- 文档路径完成一次实际远端验证；代码路径完成一次完整真实回归；手动场景入口完成一次有明确问题的迁移验证。优先合并必要验收，已通过且未再改变的场景不重复跑。
- 原本只在扩展脚本里的关键检查，要保留在那里并标明触发条件，或先迁入常规覆盖；不能因为脚本慢就直接去掉。
- 时间比较区分排队、工具安装、测试和场景实验。现有证据没有任务/安装计数时写未记录，不从用例数换算。只有实测后才写缩短了多少，不预先承诺百分比。

**停止条件：**覆盖清单、分层规则、实际运行和开发说明一致，即完成 A。没有净收益或分类过于复杂时，收缩到“保留完整代码回归、扩展场景独立触发”；不降低验证语义来追求速度。

## B：用保存材料检验能否作出判断

### 三组问题

| 问题 | 优先使用材料 | 判断范围 |
| --- | --- | --- |
| 改动后旧权限还能继续用吗？采用的基线有没有被自动换掉？ | 已有完整的 compatible check 与采用记录 | 任务、边界、约定变化和采用状态；只说明所保留验证的范围 |
| 依赖升级后，本次任务和产物有哪些变化？下一步该查哪里？ | fast-glob 升级前后 usage、跨任务记录；glob-parent 维护材料 | 版本、来源、输入/产物变化和条件；不推导包可删除或升级一定安全 |
| 报告声称通过，但材料或来源有缺口，能否相信当前结论？ | 已有缺 sidecar 的权限投影和来源不完整记录 | 能识别仅报告声明、未采集、不完整与无法确定，选择补证据或继续检查 |

### 交付与方法

制作一份小型问题集、材料清单、独立的答案依据和阅读记录模板，复用现有 [反馈模板](trial-feedback.md)。材料清单记录原提交/版本、摘要、文件来源和完整性；真实任务、适配任务、字段投影、合成反例分开标注。完整材料不存在时先缩小问题，不把补造字段或复制重复证明当作真实验证。

工程标准答案从原始报告、模型和引用核对，不能用新终端自己的输出作为唯一答案依据。首次阅读时只给问题、材料和正常使用入口，读者先自行给出“结论、依据、下一步、不能判断的部分”；答案和开发者提示之后再看，提示次数和内容都记录。

先完成材料与答案的工程核对，0 新沙箱任务、0 新安装、0 搜索。条件允许时请一至两位首次读者尝试；用户当前的手工试用也可继续提供熟悉项目后的反馈，二者不混算。不要求读者提供复杂项目或重新安装已能离线读取的原项目。

人工时间仅记录实际开始/结束及中断，未测量留空；读懂报告、发现版本变化和作出维护决定分别记录。一两个样本只支持具体反馈，不报告普遍省时、准确率提升或长期采用。当前不设置“必须比旧终端快多少”的目标，避免读者已经知道答案造成比较偏差。

### 验收与反馈处理

- 三组材料均有清楚的来源与允许结论，命令能离线工作，源材料不变。
- 工程回放能指出预期事实和关键缺口；读者能否独立找到它们另列，不将工程通过算作理解通过。
- 理解失败定位到词义、信息缺失、证据导航或配置步骤；只有这些实际问题才进入小范围修改，不先增加页面、图表或新采集器。
- 材料本身不支持问题时，修改问题或记录能力缺口；读者没有形成任何决定也保留为结果。
- 没有首次读者时完成可交付问题集，明确该效果未验证；不把开发者自测倒填成独立试用。

**停止条件：**三组工程材料可复用，取得一次有限阅读反馈，或明确记录尚无独立反馈。只围绕最主要的一至两个理解阻碍修正一轮，然后总结结果；新问题超过本阶段范围时另行排序。

## C：一次实际维护回访，按需求开展

这一步用于检验保存的证据是否真的被再次使用，不能把再跑一次已经知道答案的 Mocha 升级写成自然维护收益。

选用户现有的小项目或确有维护问题的外部项目，只选一个任务、一条路径、一次实际改动，保持原命令和适用的成功条件。权限路径复用或建立已采用基线，再 check；观察路径保存前后两次结果，再离线 inspect/compare。不要求两个路径都跑，也不要求先收缩权限。

执行前记录问题、已有材料、准备/安装需求、可信 limits 和预算。默认不搜索；材料足够的查询不再执行项目。新的单任务探索可显式采用 repetitions=1，说明它没有证明重复稳定性；已有基线不静默降低其验证要求。

在新建的单次配置下，正常兼容权限流程通常是建立和复验各一次，观察通常是前后各一次。check 失败时内部可能增加对照/确认，实际次数必须从证据记录，不能承诺固定只有两次。每条执行命令先设有限时间预算；首个失败/未知命令结束后保留材料并分析，不自动重试、重新搜索或更换实验条件。

回访记录：得到什么结论、查到哪条依据、据此检查/采用了什么、还需要哪个原有工具、配置是否继续适用、安装和任务成本、是否愿意在下次变更使用。小项目也足够，规模不是收益依据。

**停止条件：**完成一次改动及后续决定，或记录一个明确的接入/能力阻碍。没有实际改动时 C 保持待开展，不拖住 A/B，也不制造改动充数。长期维护价值继续等待真实回访，单次完成不能将其标为已证明。

## 开发提交与本阶段收口

建议按以下独立交付推进：

1. **覆盖与成本清单**：从当前脚本和已有 CI 记录整理，可只读完成。
2. **CI 分层**：实现选择规则、有限反例、默认/手动工作流与运行记录；执行语义不改。
3. **判断问题集**：整理已有材料、答案依据和阅读模板；不增加执行成本。
4. **反馈修正与回访**：按实际反馈修一至两个问题，C 有条件时开展。

每次交付只验证新改变或尚未解决的疑问，保留前次失败和成本，不反复重走全部试用。结项记录分别列出：验证维护成本的实测变化、报告帮助的具体判断、仍未验证的使用价值，以及至多两项有证据支持的后续工作。A/B 的工程交付完成即可结束这一阶段，独立理解和 C 的实际结果有则汇总、没有则保留缺口；不再以“还有功能可以加”为由延长。

共享配置、新采集器、可视化、逐包读取搜索、跨次缓存、Linux/自研沙箱继续依据 [暂缓项的进入条件](refactoring-plan.md#暂缓项及重新进入计划的条件) 排序。任何新方向先说明解决的具体问题、预期收益与最低验证成本。
