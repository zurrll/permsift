# 固定保护目标

这一轮让实验回答两个独立的问题：任务能否完成，用户指定的资源是否仍受到本次直接访问检查所验证的保护。声明是可选的；没有声明的旧配置保持原行为，内置秘密、外部写入和网络探针不会自动成为用户保护约定。

一个适合的使用场景是：构建可以生成 dist，但私人配置目录不得读取，源码目录不得修改。优先挑少数有价值的目标；不需要为所有依赖包逐一添加目标。

## 运行示例

仓库根目录执行：

```sh
npm run build
node dist/cli.js run --config examples/protection/permsift.yaml --limits examples/protection/limits.json
node dist/cli.js tighten --config examples/protection/permsift.yaml --limits examples/protection/limits.json
# 公共 CLI 的正常构建、成本记录、代码变化冲突和离线读取完整故事
npm run protection:verify
```

示例将 src/input.json 中的价格乘以数量，断言产物总额为 36。private 中只有示例假数据。实际任务输入保留原内容，探针使用另一个微型工作区。脚本另外复制一份小示例，再让构建直接读取 private/config.json：check 的旧规则和宽对照都失败，保护检查仍通过，且没有撤销保护的建议。所有输出保存在新的 .permsift/protection-validation-*，不会改写仓库示例。

## 配置及首批范围

在 scenario 下添加：

```yaml
protection_goals:
  - key: private-config
    target: '@workspace/private'
    target_kind: directory
    operation: read
    stage: task
    expected: denied
  - key: source
    target: '@workspace/src'
    target_kind: directory
    operation: write
    stage: task
    expected: denied
```

每个任务最多 16 条，key 在任务内唯一，路径最多 512 字符。目标只能是 @workspace 的严格子路径；必须在任务副本中存在，类型必须与声明一致，路径不能有链接组件。支持内部普通文件和目录，不支持任意宿主路径、缓存/临时根、真实秘密测试、根目录目标或自定义执行插件。保留的探针命名空间不能由项目配置选择。

| 声明 | 本次模拟检查 |
| --- | --- |
| read + file | 读取对应假文件 |
| read + directory | 读取一个假子文件，以及列出该目录 |
| write + file | 更新、删除、重命名对应假文件 |
| write + directory | 更新、创建、删除、重命名代表性假子文件 |
| create + directory | 在对应假目录下创建新文件 |

这些操作定义是版本化检查范围。目录检查没有穷举所有子路径。create 要求已有目录；不存在的文件不能以 ENOENT 证明“创建被禁止”。编译后 read 目标使用递归读取禁止，write/create 目标使用 SRT 的整个目标写入禁止；create 的实际规则也会禁止其他写操作，首批没有单独的仅创建权限原语。

**首批仅覆盖离线任务阶段。**安装命令保留原有安装权限，不能配置 stage: install。任务保护目标不表示安装阶段也受到同一保护。需要全流程保护的项目目前不能把本功能作为安装阶段的保证。

## 为什么先检查后端

在本机 macOS 和固定 SRT 0.0.77 上，真实实验发现：允许父目录、禁止其中子目录，可以拒绝直接读取；显式允许被保护目录或其中一个文件，则能重新打开读取。仅把 denyRead 加进配置不足以维持约定。

后端编译因此先移除完全处于读取保护目标内的正向读取例外，再增加固定禁止规则。父目录授权继续保留，未被保护的相邻路径继续按原规则执行。写入禁止也进入实际策略。每份方案保存 protection_denials，摘要同时显示正向授权与固定例外；不能把正向授权列表当成最终允许范围。移除已完全被保护禁止覆盖的授权，不再计为实际范围收缩。

这套映射只对已验证的后端/路径范围作承诺。换环境要重跑真实测试；模拟结果不能代替后端验证。

## 一次实验怎么检查

1. 保护检查只核对实际目标的存在、类型和链接组件，不把真实目标内容当作探针材料。输入快照、哈希和宿主断言仍按原流程工作；约定限制沙箱任务，不限制可信工具自身读取项目。
2. 建立另一个微型工作区，重现授权端点的文件/目录类型及保护目标的别名路径，写入随机假标记。不会复制项目源码或 node_modules，也不会把任务副本的真实输入替换成假文件。
3. 验证宿主能对假夹具执行相应访问，使用任务同一规则编译方式运行固定 Node 探针。所有目标合并为一次沙箱调用。
4. 检查夹具及实际目标条件。明确放行造成的预期变动保留为 fail；无解释的篡改、链接、类型变化或异常是 unknown，不会悄悄恢复后当成通过。
5. 实际任务前、后分别检查。安装成功后的任务与复用安装快照的任务走相同检查路径。安装失败、准备失败或检查未到达时保存 not_run；材料未保留则是 not_saved。

| 结果 | 含义 |
| --- | --- |
| pass | 目标条件、宿主对照、声明的直接操作及任务前后检查均通过 |
| fail | 对有效目标的一项直接保护探针明确被放行 |
| unknown | 目标缺失/类型改变/链接、宿主对照不成立、响应异常、超时或阶段不完整 |

任务前检查未通过时跳过任务。任务成功不能覆盖保护失败或未知；这类 trial 不能被搜索接受、发布为通过快照或导出为已验证建议。其他目标已取得的前置结果仍保留，摘要会显示 before/after 状态，不把前置通过误称为完整任务保护通过。

检查限于路径及直接操作。其他访问别名、已打开的描述符、硬链接、IPC、其他输入和恶意任务对抗都不是本轮证明范围。独立假工作区验证规则映射及目标条件，不证明真实目标在任务整个生命周期中经历过所有攻击通道。

## 搜索、回归和离线证据

run、tighten、check、observe 使用同一个固定声明和执行器；候选、恢复、宽对照及修复建议都保留禁止规则。修复器不从命中固定目标的拒绝提示生成同路径访问补充，扩大父目录授权也不能撤销禁止。

check 加载保护基线时核对对应通过 trial 的完整保护检查。增删或修改目标会拒绝继续沿用旧约定，提示先 run/tighten 建立并审阅新基线。目标顺序变化不改变约定身份。明确采用基线和约定变更的完整维护流程仍留在下一轮。

有声明的原生 executions 使用 **schema_version: 2**，保存约定、方案禁止项、保护检查及独立 outcome；没有声明的执行继续使用 v1。读取器兼容 v1 和 v2，并拒绝把 v2 新事实静默标成 v1。模型/身份版本仍为 1，已有无声明对象内容和身份保持。原 report.json、配置和 summary 的顶层 schema_version 仍为 1。

原始 evidence 保存保护探针进程、实际编译策略、宿主对照、目标条件和小夹具文件数；executions 保存规范化事实。summary.json/md 分别呈现任务、固定边界、逐条保护结果、回归阶段保护状态及证据位置。inspect 报告目录或单次 execution 可离线重读，不运行任务或安装。声明、方案或已知原始证据与原生事实矛盾时拒绝读取；哈希一致不等于生产者认证。

## 成本和验证

有声明且任务到达时，每个 trial 通常多两次沙箱调用，所有目标分别合并在任务前、后的调用内。不会为每个目标另跑一次项目或安装。微型副本只创建授权端点和少量假文件；成本受声明数量和路径数量约束，不随 node_modules 文件数量复制扩张。

timings.phases.protections 记录准备、检查和清理耗时；摘要增加 protection_cost。无声明配置没有这两次调用。对照脚本保存有/无目标的单次总耗时与保护阶段耗时；一个本机样例只能说明实测开销，不能证明普遍性能收益或用户节省时间。

测试覆盖真实父/子读取例外、任务输入不被替换、搜索/恢复/导出/重放、任务与约定冲突、允许的精确读取修复、依赖观察、共用/分开安装策略及安装快照复用。反例覆盖 ENOENT、链接、文件变目录、夹具篡改、缺操作/对照/阶段、明确放行、原生结果篡改和缺少保护基线证据。所有保护检查都是额外证据，不替代原产物断言和固定边界检查。
