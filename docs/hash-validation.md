# 完整性校验的成本与一致性

v0.8 优化安装快照的完整内容扫描。一次任务试验仍核对冻结源和本轮副本，两次核对各遍历 workspace、cache、tmp。捕获快照仍核对来源和冻结副本；最终策略仍从原始输入重新安装。执行方式、权限搜索、恢复和边界探针没有更换。

## 优化范围

旧扫描器对每个条目顺序调用 realpath、lstat、stat，再逐文件 readFile。新扫描器对目录复用 lstat 属性；普通文件在打开后用文件描述符 stat 核对类型、inode、设备、大小和权限，避免把路径上随后替换的文件当作原条目。

I/O 最多并发 8 个操作组。目录子条目以最多 8 项批次查询；小文件读取采用有界队列。哈希更新仍按旧版排序后的深度优先顺序执行，路径、文件权限、内容长度、全部内容、规范化内部链接和可选目录权限的序列格式不变。不是把每个文件的新摘要拼成另一种树哈希；稳定输入产生原来的 SHA-256，可继续导入历史报告。

每个小文件最多分配 1 MiB，最多 8 个待消费文件缓冲；大文件用 64 KiB 缓冲逐块读取，期间先耗尽小文件队列。所有内容实际读取，不以大小、时间戳、克隆请求成功或历史内容缓存替代。文件长度变化、异常类型、外部或循环链接、取消和超时均不能返回通过用的摘要；错误返回前等待已排队的 I/O 结束并关闭已打开文件。取消和截止时间在 I/O 前后及分块边界协作检查，不能强制中断底层尚未返回的文件系统调用。

这些检查不提供整个目录树的原子快照，也不保证抵抗具有相同用户权限的恶意宿主进程；沿用可信任务、受审阅输入和隔离副本的范围。摘要仍不覆盖时间戳、所有者、ACL、扩展属性、文件 flags 或物理共享块。

## 报告字段

timings.hash_scan 在使用内容扫描时出现，记录 scans / incomplete_scans（根扫描数及未完成数）、files / directories / symlinks（累计访问次数）、content_bytes（实际读取字节）、concurrency / peak_buffered_files（I/O 上限及小文件缓冲峰值），以及 operations 的 realpath、lstat、stat、readdir、read、digest 调用数与 service_ms。read 包括打开、读取和关闭；stat 包括文件描述符核对。

service_ms 是每次调用的起止时间之和，并行时会重叠，**不能相加当成总墙钟或 CPU 时间**。独占总时间继续以 phases.hash 为准。旧版 readFile 内部还有打开/属性/读取/关闭调用，参考脚本只统计一次公开 API 调用；read 调用数不是底层系统调用次数，也不宜用新旧调用数直接推导开销。

## 复现诊断

```sh
npm run medium:prepare
npm run hashes:benchmark

# 有上轮证据时，复用同一暖种子和输入
npm run hashes:benchmark -- --baseline .permsift/fast-glob-profile-XXXXXX/summary.json

# 同一输入、同样时间预算，v0.7 与当前实现顺序比较
npm run search:benchmark -- --baseline .permsift/hash-benchmark-XXXXXX/summary.json --seconds 300

# 保持原候选和预算，核对每轮权限/结论及最终规则
npm run medium:verify -- --baseline .permsift/fast-glob-profile-XXXXXX/summary.json
```

hashes:benchmark 缺少基线时先做一次沙箱冷安装验收，再固定缓存种子。随后执行三次真实暖安装，在安装通过、目录准备和输出刷新之后，任务读取夹具、离线探针和命令之前，观察三根摘要和文件清单。执行器的 measureInstalledState 诊断选项显式增加扫描；默认实验不做这些扫描，也没有新增用户配置字段。

扫描对照使用小型夹具和完成真实任务的一份安装树，同一树交替运行旧版参考、并发 4、并发 8，共三组。每次三根哈希必须一致。参考实现在 test/support/reference-hash.ts，只用于兼容性测试和性能观察，不在生产路径内。结束时清理保留的实验副本。

传入 medium:verify 基线时，另外从该基线的 recommended.yaml 观察三次收紧后的安装状态，并要求两组冻结输入相同。初始宽安装规则与已验证收紧规则分开记录；默认从头诊断没有历史推荐规则，只观察初始规则，不自动做一次完整搜索。

search:benchmark 从本地 Git 读取固定 v0.7 提交 0b457b5，构建临时参考执行器，共用现有工具依赖，不重新安装工具依赖。两轮顺序使用同一暖配置、相同时间预算，候选上限都提高到 200，任务仍在沙箱中执行。检查输入、配置、预算、Node/npm/后端、共同前缀的每轮权限/结论，以及最终三次全新安装通过；参考 checkout 在结束时删除。

等候选用于确认相同比较的耗时与结论；等时间用于观察同预算能完成多少候选，不能替代前者。默认示例仍是 40 个候选，提速不会自动提高用户上限。32 条授权及有界枚举限制仍存在，更多时间不意味着 node_modules 能展开到每个包。

## 暖安装一致性的解释

分别比较 workspace、cache、tmp，保留新增、删除和内容变化路径。只测到 workspace 相同，不能推出完整安装状态相同；三次相同也不证明未来所有安装确定。摘要只覆盖既定字段。

安装权限也是观察条件：允许写缓存/临时目录时可能生成不同日志和编译缓存，只允许写 node_modules 时这些写入受限。本机分别观察到初始宽规则下缓存/临时状态不同，以及已验证收紧规则下三根一致；不能忽略权限条件推导任何一种执行方式普遍等价或不等价。

实测差异、耗时和测试结果见 [validation.md](validation.md)。微基准使用稳定、已访问的树，不是新克隆树的成本模型，也不替代完整搜索时间。所有时间均是单机观察，受文件系统缓存和负载影响。
