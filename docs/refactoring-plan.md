# Permsift 整体重构计划

2026-10-02。基于 v0.12.0 / 0401304，处于计划阶段，本文不表示功能已经实现。

## 这次重构要达成什么

保留并整理已经建立的严肃实验底座，在其上形成两条能够独立使用的路径：

1. **权限路径**：建立适合真实任务的规则，理解失败，在项目变化后复验、审阅并采用新的方案。
2. **依赖观察路径**：观察真实任务中的模块、编译输入和产物记录，查询、比较并理解变化。

两条路径共享执行与证据基础，各自验证使用价值。依赖观察不要求先做权限搜索，其收益也不以减少权限试验为唯一标准。

这是一项跨多轮开发的重构，不把每一轮等同于一个版本。每轮有可运行的交付物和验收条件；试用发现问题后允许调整后续设计。项目仍是开源学习项目，同时检验这些能力能否进入实际开发流程。

## 重构期间保留的成果

- 冻结输入、独立工作副本、独立缓存和临时目录；原项目与管理证据的保护。
- 安装和任务分阶段、任务断网、可信权限上限、后端真实执行。
- 输出刷新、声明式断言、前后边界检查、宿主对照、失败恢复和最终复验。
- 超时、中断、有限输出、进程清理；证据及时保存和未知结果的处理。
- 来源分别记录：模块加载、编译输入和产物记录具有不同含义、覆盖范围与健康度。
- 快照和完整性检查；复用安装状态的条件以及最终重新安装的要求。

底座的整理须保持这些行为。测试通过数量、规则数量、加载包数量均不能替代用户收益。

## 共同模型：先厘清含义，再决定文件与命令

| 对象 | 内容 | 需要分开的角色 |
| --- | --- | --- |
| 任务定义 | 命令、安装条件、准备状态、产物与成功条件 | 描述任务，不隐含批准新增权限 |
| 保护约定 | 要保护的资源、操作、阶段，以及可执行的检查期待 | 人的保护意图与实际验证范围分别记录 |
| 权限方案 | 安装和任务的具体授权、读取目标类型等 | 初始方案、宽对照、候选、建议、已采用方案分别识别 |
| 执行条件与证据 | 输入、环境、实际命令、策略、检查方式、任务与采集结果 | 事实、来源健康度、对照关系与推断分别保存 |
| 已采用基线 | 明确选择的方案、对应约定与条件、验证证据引用 | 成功报告不会自动成为最新采用基线 |

可信 limits 保持独立，约束所有执行、对照和补充建议。用户入口不必拆成五个文件；内部角色分开也不能以增加用户配置负担为代价。

五对象是待检验的职责划分。第一轮须先确定各自的用途、身份、引用、生命周期与缺失信息含义，再用权限、回归和观察案例检验这些边界。字段、模块和公开格式可以在后续轮次修订；不能为了保持“五个”这个数量，把难以归类的运行条件或证据硬塞进某个对象。

### 结论至少保留四个维度

1. 任务和声明的成功条件是否通过。
2. 边界期待是否通过，实际检查了什么，是否缺少对照或证据。
3. 每种观察来源是否采集、是否完整。
4. 搜索、比较或回归流程是否完成，是否有需要审阅的变化。

例如，任务通过、模块记录不完整和搜索受预算限制，可以同时成立。摘要须说明相关缺口，不能用一个绿色状态掩盖其他维度。

### 前后变化必须分清

- 项目输入改变。
- 任务、成功条件或保护约定改变。
- 权限方案改变。
- 环境、准备条件或采集方式改变。

旧权限在新成功条件下通过，与原约定在项目变化后仍成立，是不同结论。第一轮建立区分方式，第五轮落到基线维护流程。

## 环境与接入检验：从第一轮开始

第七轮汇总完整使用流程和复现结果。第一次换环境、第一次让未参与开发的人接入，尽早开始；它们暴露的问题可能影响对象身份、环境条件、配置边界和证据解释，须及时反馈到模型。

| 时点 | 实际检验 | 怎样使用结果 |
| --- | --- | --- |
| 第一轮开始 | 用现有版本建立环境基线，检查 doctor、最小权限演示、保存报告的离线查询与比较 | 记录当前能运行的条件和接入障碍，作为模型与迁移的参照 |
| 第一轮内尽早 | 在另一台受支持 macOS 或实际目标 CI 上重放最小流程；条件允许时，由未参与开发的人照文档接入 | 将不同安装位置、环境能力、路径、报告迁移和理解成本的问题带回模型设计 |
| 第二轮及后续各轮 | 在真实后端上检验受影响流程，核心执行迁移完成时做完整集成验证；新模型和摘要持续接受已有案例及试用反馈 | 验证底座行为，并修正新设计；离线回放不能代替真实隔离检验 |
| 第七轮 | 汇总两条完整使用路径的接入、自然改动、回访和跨环境复现记录 | 判断整体重构是否达成用户目标，列出仍未验证的范围 |

第一次跨环境检验采用小而完整的流程，优先暴露能力和接入问题，不重复大规模权限搜索。没有第二台机器、CI 执行条件或独立使用者时，第一轮就准备复现材料并登记缺口；不能等到第七轮才发现条件不足，也不能把材料准备好写成已经通过。已具备条件的工作继续推进。

## 七轮开发与验收

顺序代表依赖关系，不是固定发布时间。共同底座抽取可以在第二轮中拆为几个小提交；后续使用检验贯穿各轮。

| 轮次 | 目标 | 可 review 的交付 | 进入下一轮的条件 |
| --- | --- | --- | --- |
| 1 | 统一任务、方案、证据与结论的内部含义 | 内部类型、旧数据适配、两条完整使用案例、兼容样本、判断表和早期环境检验记录 | 模型能解释代表案例，身份和缺失含义明确；实际反馈或未验证缺口已记录 |
| 2 | 整理共同执行底座与流程边界 | 一次受控执行的接口，独立流程编排和报告呈现 | 现有真实验证成立；任务、策略、阶段和来源证据一致 |
| 3 | 让两条路径的结果容易理解 | 权限与观察的分别摘要，变化分类、证据索引、行动说明 | 已保存报告可离线解释；失败和缺口在摘要中可见 |
| 4 | 把用户保护目标变成可验证约定 | 有限的目标声明、独立检查夹具、逐目标覆盖说明、方案约束 | 真实拒绝、错误放行和无法验证都能正确区分 |
| 5 | 明确基线采用与约定变化 | 基线描述、明确采用入口、约定变化审阅、回归与重放 | 原约定保持与新约定验证不会混淆，建议不自动采用 |
| 6 | 诊断成功条件的具体能力 | 可选的产物扰动检查、范围说明与建议 | 诊断不冒充完整测试质量，不影响原输入和既有验证结论 |
| 7 | 简化接入并汇总完整使用检验 | 精简配置、两条入门说明、实际改动记录、贯穿各轮的环境复现结果 | 两条路径各能解决明确问题；接入和回访成本有实际记录 |

## 第一轮：模型、案例和兼容样本

2026-10-02 已实现本轮内部适配层、真实样本与本机最小验证。交付及边界见 [模型](model.md)、[案例](model-cases.md) 和 [环境检验](environment-validation.md)。跨环境及独立接入仍未验证，执行底座迁移留在第二轮。

**做什么**

- 从 config、engine、regression、observation 和 usage 报告中整理上述角色，建立内部模型和结论判断表。
- 明确成功条件、保护期待、权限上限和采集设置的不同用途；确认哪些改变需要提示重新审阅。
- 通过适配器读取当前配置和报告；先保留现有 CLI、配置结构、报告格式和退出码。
- 设计两条可重放案例，记录当前事实与成本。权限案例覆盖代码新增读取、普通任务错误和规则补充；观察案例覆盖依赖升级、跨任务定位和产物差异。
- 梳理两条路径的现有用户步骤，区分初始化、一次执行、再次查询与后续维护。
- 建立最小环境基线和复现材料，尽早开展跨环境与独立接入检验。环境问题和理解困难直接用于修正模型。

**模型必须回答的问题**

- 对象的身份由哪些内容决定？项目内容变化、任务定义变化、权限变化和环境变化分别怎样识别？
- 谁生成或选择这个对象，什么时候可变，什么时候应当冻结？成功记录与已采用基线怎样区分？
- 对象之间引用什么，怎样检验引用一致？旧证据的身份与哈希不能因新模型归一化而被改写。
- 部分结果、未知、未采集、未声明和未保存怎样表达？哪些结论可以由事实推导，哪些必须保留缺口？
- 代表案例是否需要大量特殊分支才能表达？出现这种情况时，先修正边界，再开展大范围执行迁移。

**交付**

- 内部模型与判断表、迁移映射文档和一组有来源说明的兼容样本。
- 优先复用现有 demo、规则回归案例、fast-glob 保存记录及 glob-parent 试用结果，避免为了模型讨论重新安装或搜索。
- 真实记录、字段投影和新造的反例分别标注来源。
- 最小环境执行记录、跨环境复现材料、独立接入反馈；尚未获得实际结果的部分标为未验证。

**验收**

- verified 但搜索未完成、任务通过但采集不完整、任务失败但记录完整等组合能独立表达。
- 旧报告没有保护目标时，显示未声明；没有来源时，显示未采集或未保存。
- 当前判断结果和事实不因适配而改变。模型新增内容尚不能推导时，保留缺口。
- 任务成功但采集不完整、约定改变后旧规则通过、恢复不稳定、读取目标类型改变，以及安装与任务权限不同等案例，都有清楚的对象关系和结论依据。
- 身份与引用在重复适配时稳定；模型自身修订不能冒充项目或用户约定变化。

这是实际开发的起点。先稳定最小接口及其含义，保留模型修订机制；完成后依据案例与环境反馈修正第二轮接口。

## 第二轮：共同底座与流程编排

2026-10-02 已完成核心迁移。可执行请求、单轮执行、逐轮保存、类型化阶段事实和报告呈现分别成模块，check/observe 已接入，新增原生模型文件与索引；实现与边界见 [共同执行底座](execution-foundation.md)，实际验证见 [环境检验](environment-validation.md)。

**做什么**

- 将 engine 中的一次受控执行、流程决策、报告渲染逐步分开；regression 调用共同执行能力，减少对整份实验报告的再次解释。
- 一次执行接收明确的任务、方案、条件、预算与采集设置，返回任务、检查、日志、变化和各来源结果。
- run、tighten、check、observe 保留独立流程，分别管理重复次数、候选、恢复、宽对照、最终验收和采集。
- 报告与离线分析继续作为证据的投影，不承担实际任务执行。

**验收**

- 原项目保护、输出新鲜度、独立副本、进程清理、未知结果、真实边界、安装分阶段和导出重放都保持。
- 观察预加载的额外内部写权限、TypeScript 实际命令变化、esbuild 输出刷新继续进入执行条件和证据。
- 比较稳定的策略、断言、边界与决策事实，不要求时间、随机 ID 或临时路径逐字相同。
- 冻结输入、安装复用条件、可信上限和最终重新安装要求仍被验证。

本轮完成核心迁移，不同时修改搜索算法、增加试验并发或引入跨次缓存。

## 第三轮：分别服务两条路径的摘要

**权限摘要回答**

- 这次采用什么方案，任务和边界检查结果如何？
- 哪些规则被接受或拒绝，依据是哪次执行和恢复？
- 搜索是否完成，哪些范围没有尝试？
- 当前方案是验证结果还是待审阅建议，怎样重放？

**观察摘要回答**

- 本次比较哪些任务，项目和执行条件发生了什么变化？
- 哪些包实例、编译输入或产物记录变化，怎样定位细节？
- 哪些来源没有采集或不完整？
- 这些事实可以支持继续检查哪里，哪些结论仍无法判断？

**验收**

- 使用同一份规范化事实生成 JSON 和文字摘要；结论链接到相应证据。
- 旧报告可离线生成摘要，无需原项目、安装或任务执行。
- 任务未运行、来源缺失、unknown、约定改变、预算停止、零字节贡献等不会被省略或误写为成功。
- 两条摘要保持不同用途，观察差异不自动成为权限补充或删依赖建议。

## 第四轮：保护目标及其覆盖

**首批范围**

- 仅支持任务阶段、工作区内有限的文件或目录目标，例如一个配置文件的直接读取应被拒绝，源码目录中的文件创建应被拒绝。
- 将资源路径与类型、操作、阶段、检查方法、前后结果、宿主对照和证据引用关联到每条目标。
- 用户的高层意图与本次已测试期待分别显示，不把一次直接访问检查称为所有访问通道都安全。

**设计与实现顺序**

1. 先验证底层规则组合及路径语义，确认目标在所支持后端上能够准确表达。不能假定 deny 与父目录 allow 的组合总有预期优先级。
2. 制定目标与候选、宽对照、补充建议的兼容检查。强制保护目标保持固定；与之冲突的方案不能成为可采用建议。
3. 用假数据建立独立的探针副本，验证与任务方案对应的资源别名、路径类型与条件。不得把任务副本的真实输入替换成假数据，扰动任务行为。
4. 支持范围不明确、对象类型改变、资源缺失或宿主对照不成立时，报告无法验证；不能把 ENOENT 当成拒绝。

**验收**

- 错误放行、明确拒绝、资源不存在、路径链接、文件变目录、探针异常与夹具篡改都有区分。
- 前后检查适用同一目标和方案，任务成功不能覆盖保护期待失败。
- 所有执行流程使用同一目标判断方式；check 的宽对照及自动补充也受约定约束。
- 先用真实后端反例检验方案表达与探针方法，再扩展目标种类。

任意宿主路径、真实秘密、所有网络通道、IPC、恶意任务对抗与通用自定义探针插件不进入首批范围。

## 第五轮：基线采用、约定变化与日常维护

**做什么**

- 为已采用基线建立可读取的描述：对应的任务和约定身份、权限方案、验证条件、原始证据引用。
- 提供明确选择基线的入口。具体命令名由前几轮的使用结果决定，不靠“最新成功报告”自动切换，不增加反复确认弹窗。
- check 分别说明约定是否变化、旧方案对当前任务是否兼容、哪些范围需要审阅。
- 增减任务、更换成功条件或保护目标时，保留历史定义与变化内容，并明确当前验证范围。
- 权限建议经过验证后仍是建议；明确采用后才成为后续维护的参照。

**验收**

- 同一约定下的输入变化、新约定下的旧规则通过、普通代码错误、明确权限变化和未知结果可区分。
- 删除成功检查或保护目标不会被摘要表达成原约定全部保持。
- 新增任务未验证时，不宣称整组约定已通过；已有任务的有效结果仍保留。
- 基线证据缺失、身份不一致、条件改变或目标类型改变，保留原因并要求相应审阅或新验证。
- 已采用方案可重放；继续以独立 limits 校验。引用和哈希校验不冒充报告签名或生产者认证。

## 第六轮：可选的成功条件诊断

**做什么**

- 首批只检查产物缺失、清空，以及适用的结构化内容改动。记录具体扰动和哪条断言检测到它。
- 使用独立产物副本，诊断结束后保留原始通过记录；不修改原项目、原证据或采用基线。
- 默认不为此重新安装或运行任务，额外开销只来自产物复制和宿主断言；设置大小、数量和时间上限。

**验收**

- file_exists 检测不到空文件时，准确说明它只检查存在等已支持条件，不自动判为错误配置。
- 多条断言的共同作用与单条作用分别说明，不能仅统计每条是否检测到扰动。
- 任务内部的行为测试、其他输入和未知业务错误不在本次诊断覆盖内。
- 不输出整体测试质量分数，不把诊断通过作为权限安全或任务全面正确的证明。
- 支持跳过和不适用，结果作为改善成功条件的线索，不静默改变候选接受标准。

规划意见中关于 clsx 的“五个空文件也能通过整套验收”不成立：任务还加载五种产物并检查行为。可保留的判断是，那五条存在断言本身不能检测空文件。诊断与任务验收范围须分别表达。

## 第七轮：接入简化与完整使用检验汇总

**做什么**

- 根据前几轮的实际步骤简化配置，避免任务定义、安装设置和方案在多个导出文件里反复复制维护。
- 允许必要的共享声明，但最终执行前显示或记录展开后的配置、来源和授权；可信 limits 仍由用户显式提供。
- 分别提供权限入门和依赖观察入门，README 首先帮助用户选择问题，再指向完整参考与实验细节。
- 对一个持续维护的真实项目完成两条路径中的实际问题记录，尽量保留原命令、测试和构建。
- 更新第一轮开始准备的跨环境复现材料，汇总各轮执行和独立接入结果，补齐尚未覆盖的完整使用流程。只有实际执行后才记录环境通过。

**记录成本与收益**

| 时点 | 记录什么 |
| --- | --- |
| 首次接入 | 修改原项目的内容、包装脚本、配置、手动步骤、用户需作的判断、支持限制 |
| 执行 | 安装次数、任务次数、探针与校验成本、总等待、失败重试 |
| 再次查询 | 是否需要原项目或重新执行，定位到结论和证据的步骤 |
| 后续改动 | 配置修改量、约定变化、基线审阅与重放步骤 |
| 使用结果 | 回答了什么问题，使用者据此检查或采用了什么，仍缺哪些信息 |

这些记录从第一轮开始，最后汇总；人工时间仅在实际记录时报告。不能用配置行数或 CLI 墙钟时间推导节省的人工分钟。

**验收**

- 权限路径完成建立、采用、项目改动、回归判断及必要的建议重放。
- 观察路径完成采集、保存、离线查询及一次真实变化的解释，不要求运行权限搜索。
- 使用者能从摘要找到结论、范围和依据，额外适配及失败接入也被记录。
- 尚未获得另一环境或使用者的执行结果时，明确保留验证缺口，不以新增 CI 文件代替。

## 迁移方式与开发约束

- 旧配置与报告通过适配器进入新内部模型；先保留原 CLI 行为。需要新公开格式时显式区分版本，提供迁移示例。
- 不覆盖或重写历史证据；新增保护目标不倒填为旧实验已经验证。缺少的字段保留缺失状态。
- 每轮能独立构建和运行。修改共同执行、配置或后端时，覆盖受影响的真实流程；核心执行迁移完成时运行完整 macOS 集成验证。
- 摘要、离线模型和文字改动优先使用保存记录及反例回放，不为了排版反复下载依赖。
- 真实网络与中等项目实验用于明确的安装、准备或完整流程疑问，记录测量条件；已解决疑问不重复跑来增加通过数量。
- 把行为重构、规则语义变化和性能优化分开提交，便于定位回归。用户实验成本与开发回归成本分别记录。

## 暂缓项及重新进入计划的条件

| 项目 | 什么证据会使它值得进入 |
| --- | --- |
| 同一 observe 内共享安装 | 多任务使用的安装成本确实阻碍使用，且完整条件匹配和副本校验后有净收益 |
| 内嵌依赖、生命周期脚本、其他安装布局 | 选定真实使用流程被其阻塞，并能设计明确的安装边界与验收 |
| 新采集器或可视化 | 现有来源和摘要无法回答一个具体、有用的问题 |
| 更细的读取搜索 | 指向有价值的保护范围，少量试验能带来明确结果 |
| Linux、其他后端或自研沙箱 | 目标使用环境或当前后端限制形成实际阻碍，能够独立验证其语义 |

暂缓不等于永久拒绝。新发现可以调整优先级，但须说明解决的用户问题、预期收益和验证方式。

## 整体完成的判断

本轮重构完成时，应能交付共同底座清楚、两条路径独立、结果可理解、历史可解释的工具：

1. 用户能选择自己的问题，了解需要提供什么与将得到什么。
2. 每个结论都能定位到条件、实际检查方式和证据，未知与未覆盖可见。
3. 权限用户能建立、采用并维护方案，约定变化不会被当成无变化。
4. 观察用户能独立理解任务和依赖变化，保存记录可以继续使用。
5. 底座原有隔离、一致性、恢复、清理和最终验证能力经真实执行确认。
6. 使用与环境验证的实绩、失败及缺口都有记录，后续方向据此调整。
