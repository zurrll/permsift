# 开发讨论：成本、明确结果与版本节奏

2026-10-05。基于本地提交 1b3f9f1、远端已通过 CI 的 5d7f957。本文记录用户提出的问题、此次核对和后续设计方向；不表示已修改工作流、采集器、搜索模式或版本号。本次只读取代码、已有实验材料和 GitHub 元数据，没有新增项目任务、安装、权限搜索或 CI 调度。

实施补充：用户随后要求暂缓权限收缩策略，先做简单 CI 调整和重型工具链问题。当前实现只加入过时运行取消、纯文档路径识别，以及 [v6 加载/解析预算分离](load-and-resolution-budgets.md)。权限候选、恢复和最终验证策略保持现状；本文第四节继续作为待讨论设计。完整的结果表达调整和集中升版也未在这轮实施。

## 需要持续保留的五个问题

1. CI 实际消耗多少，有没有月度额度风险？能否减少不产生新信息的执行，同时保留必要覆盖？
2. 恢复版本发布，但开发轮次不再等于版本号；以用户能使用的完整变化作为发行单位。
3. 工程记录要准确，产品输出也要清楚告诉用户已经知道什么，避免通篇限制掩盖有用结果。
4. 权限搜索不能默认把每次失败都当成需要完整调查的事件；重新比较逐次恢复的收益与成本。
5. 单文件 XO 对照已经说明工具链自身能耗尽模块事件预算。研究加载事实和解析明细分别保留，而不是只提高上限或把工具链依赖过滤掉。依据见 [工具链预算实测](toolchain-event-pressure.md)。

共同原则：对每笔新增成本说明它支持哪个用户判断。得到可用结果、解释失败原因、证明采集范围和开发回归是不同目标，不能要求每位用户在每次运行中都购买全部证据。

## 一、CI：目前不用担心这份仓库的执行分钟额度

GitHub API 确认 zurrll/permsift 是公开仓库；当前工作流使用标准 ubuntu-latest / macos-latest runner。公开仓库的标准 runner 执行分钟免费，不消耗私有仓库对应的月度分钟额度。[GitHub 官方计费说明](https://docs.github.com/en/billing/concepts/product-billing/github-actions)。这是本仓库执行分钟的结论，不是整个 zurrll 帐号所有产品的账单结论。

最新默认 CI 的等待时间约 7 分 53 秒，机器时间合计 14 分 23 秒。两组 macOS 并行缩短了等待；不能把并行缩短的墙钟时间当成等量的算力节省。当前默认仍保留全部 82 个集成用例（69 core + 13 install），两组 Linux 单元及离线入口、macOS 单元、doctor 和 bundled 公共 CLI 验证；扩展场景改为手动入口，见 [覆盖与收据](ci-validation.md)。这些范围与旧默认不完全相同，不能把旧总时间与新等待时间直接当作同条件性能对照。

当前 artifacts API 返回 9 个未过期保存包，size_in_bytes 合计 37,979,152 字节，约 38 MB（36.22 MiB）；缓存 API 返回 2 个缓存、42,280,373 字节，约 42 MB（40.32 MiB）。保存包大小只是当前元数据，不是整帐号的存储用量或按小时累计账单。官方另有 artifact/Packages 共用存储额度和每仓库缓存额度，因此不把“执行分钟免费”扩写成“所有资源永远免费”。帐号账单 API 在当前凭据下不可读，本次没有扩大令牌权限。

### 值得做的小幅调整

- 同一分支的新提交取代旧提交时，取消尚未完成的旧默认运行；为手动、发行等不能被普通 push 取代的运行保留独立组。
- 明确的纯文档变更省去真实沙箱作业。使用有限文档白名单，检查完整 diff；未知文件、混合改动、无法取得比较起点时仍跑完整回归。保留清楚的汇总状态，不能把缺执行伪装为通过。
- 避免同一改动在 push 与 PR 上重复执行完全相同的回归；实现前确认分支保护、贡献者 fork 和事件身份，不能简单关闭某一种事件造成漏检。
- 合并完成的小改动后再推送；讨论记录可以先留本地。保留有效 npm 缓存。保存材料设置明确保留期限，成功与失败分别考虑，不能为省空间丢掉当前诊断所需证据。

以上主要减少重复触发。暂不按几十个源码模块选择集成测试、不减少重复稳定性要求、不删除独有反例、不靠失败自动重试制造绿色结果。当前没有额度紧迫性，复杂调度系统本身也有维护成本；省下几分钟不值得先开发一套庞大的测试选择器。

2026-10-05 用户补充：既然 CI 没有额度压力，只做简单调整，不深入优化。上述清单是可选方向，不要求全部实施；优先评估取消过时运行和纯文档路径，涉及额外事件路由或存储管理复杂度的工作暂缓。重型工具链的采集预算问题仍须处理，不能因收紧 CI 范围而遗漏。

## 二、版本：发布代表交付，轮次代表工作

package.json、package-lock.json 和 src/version.ts 仍为 0.12.0；CHANGELOG 的 Unreleased 已积累整体重构及后续修复，当前本地没有版本 tag。继续长期把所有东西堆在 Unreleased，会使用户难以知道自己装的代码与文档描述是否对应。

建议恢复以下节奏：

- 每轮开发使用普通提交和 Unreleased 记录；一轮结束不自动改版本号。
- 一组可使用的能力完成、说明与兼容关系清楚、必要回归通过后，集中准备一次发行。测试只为新变化和未解决问题服务，不为发行再重复无关实验。
- 兼容的缺陷修复可以发补丁版；形成新的完整使用能力时发次版本。即使仍在 0.x，也明确说明配置、CLI 和保存材料的兼容变化。
- 工具版本、内部模型格式和观察日志格式分别管理。日志 v5 不等于工具 v0.5，也不能仅凭工具版本认定两份材料可直接比较。

下一次可以为现有积累准备 **0.13.0**，按“接入与配置解释、建立/采用/复验、保存材料的离线判断、依赖来源查询”整理面向用户的变化。发布前做有限收口，不再把七轮内部重构逐轮当作七个用户特性。模块预算或搜索模式是否进入这次发行，取决于它是否完成；版本号不能反过来要求把所有待办塞进同一个版本。本文没有实际升版、打 tag 或发布包。

## 三、表达：先交代已经得到的答案

用户指出的问题成立。工程数据区分 pass/fail/unknown 是必要的，但默认界面反复强调所有普遍限制，会让已经成立的结果失去位置。准确不要求每句话都从“不知道”开头。

当前有具体改善点：terminal.ts 的 summary.partial 会在多个流程中覆盖原结论标题；注意事项排在任务事实之前。result-explanation.ts 的来源说明也容易把状态和多项限制塞进同一句。这些行为可能把某一来源的缺口扩大成整个工具没有结论。

建议默认输出依次回答：**完成了什么、发现了什么、哪个缺口影响当前判断、接下来有什么具体行动**。常驻的能力边界和详细依据放到保存报告或按需入口；真正的任务失败、边界异常、材料损坏仍应突出。不能为了口气肯定而把 unknown 改成 pass。

例如本次 XO 材料可以说：

> lint 任务通过；已记录 325 个包实例的加载。模块明细达到事件上限，完整加载总数尚未得到。

这里“任务通过”和“确实留下加载记录”是有用的正面事实；325 不能改写成全部依赖，也不能据此给未记录依赖下删除结论。工具链模块也是任务的实际依赖，不按名称过滤。

权限复验通过时先说“旧规则本次复验通过，可以继续用于这组任务”，随后简述验证条件。Node 来源不完整时只标记 Node 来源，不盖掉已完成的 TypeScript 输入或构建产物输入。未采集、没有记录、没有产物贡献分别表述。不是每条成功结果都需要重复一整段全局保证的限制。

### 如何检验这类修改

优先复用现成的完整、截断和损坏材料，给出能独立核对的预期事实，检查第一屏是否保留正确结果、关键异常是否显眼。表达调整用离线回放和有限反例验证，不为了测试文案重跑大型 lint 或搜索。首次读者的反馈有价值，但不作为完成工程修正的前置条件；人工阅读效果与程序检查分开记录。

## 四、搜索：逐次恢复有收益，但默认收益目标值得重审

当前 search.ts 对每次未通过的候选（fail 和 unknown）都执行当前已接受策略的恢复；恢复不通过就将比较记为 unknown 并停止。execute-once.ts 为每次执行创建独立副本，失败现场不会被下一次复用。因此这里的“恢复”主要是新鲜的对照实验，不是修复被候选污染的工作目录。

历史 clsx 优化从 190 次降到 89 次，其中恢复从 76 次降到 31 次。优化后恢复仍约占 trial 数的 35%，但各 trial 的耗时不同，不能直接声称会节省 35% 时间。分组缩减、按轮复查、同轮相同失败组合的调度线索和无变化阶段避免重搜已经存在，不能作为待开发的新优化重复计算。依据见 [实测记录](validation.md)。

逐次恢复提供的是“这次候选未通过，随后当前策略在干净副本中通过”的证据。它有助于定位不稳定，也支持拒绝候选的解释；单次恢复仍不证明某个权限在所有环境下都必要。最终重复验证则回答另一个问题：“输出的这份规则能否完成声明的任务”。

### 推荐先设计两种使用目标

| 目标 | 保留的核心检验 | 对失败的处理与允许结论 |
| --- | --- | --- |
| 寻找可用的较小规则 | 固定输入与条件、独立副本、每个接受候选实际通过任务/边界检查、最终从干净状态完整重复验证 | 普通失败可以保留原授权，减少逐次对照；无对照的失败不能解释为已证实授权必要 |
| 调查收缩失败的原因 | 在上述基础上，保留目前逐失败的新鲜控制 | 为各次拒绝留下明确比较材料；仍不保证唯一原因或全局最小 |

这是推荐设计方向，尚未确定默认模式、参数或具体调度。低成本模式仍会可能多留一些权限；它更关注“交付已经验证的较小规则”，不要求解释每个没有接受的收缩。减少对照会降低失败诊断的密度和对环境波动的发现速度，不能声称与现有模式所有效果相同。

实现前须明确以下事项：

1. 普通任务失败与 unknown、超时、保护/边界异常分别处理；不能把采集/基础设施故障当作权限不足继续推断。异常应及时检查或停止。
2. 没有新鲜恢复的拒绝不能拥有当前恢复支持等级，不能填一个旧 recovery_id 冒充本次执行。搜索完成、候选调查程度与最终验证状态分别呈现，审查现有 search_complete 的含义和旧材料兼容。
3. 当前策略一旦接受变化，旧失败线索不能永久当作“必要权限”。保留非单调性复查纪律。
4. 时间预算包含候选、控制和最终验证；预留完成可用输出所需的验证机会，而不把所有资源花在细枝末节上。
5. 比较成本用已有报告先做分解；真正验证节省时只选一个有代表性的任务，记录候选数、控制数、最终验证、耗时、结果与解释差别，不再无问题地重跑所有项目。

同一固定策略下的有界控制批次可以作为第二种研究方向：若数个失败候选共享一个后续新控制，记录批次、控制策略身份、执行引用与间隔；策略变化或控制异常就结束批次。它不能假装与每个候选紧邻控制完全等价。

对于根本没有改变有效授权的配置整理，可先统计出现频率，再评估是否能证明后端规则及保护检查等价后直接规范化。不能只比较路径包含关系。也不因输入路径相同就省略安装快照完整性检查；这种检查若要优化，先建立可信的不可变输入保障。

## 五、模块预算：保留事实的顺序要符合用户用途

单文件 XO 对照已经有足够材料支持设计工作，无需再次执行相同任务来证明它还会触顶。后续应先分析保留事件的构成，评估加载模块/包事实与解析关系分别设限或汇总的方案，同时保留总资源上限、worker/footer 健康状态和离线一致性。详细解析停止不能自动让基本加载事实停止，也不能把基本事实仍能记录误称为全部来源完整。

新设计需要分别回答：实际保留了哪些加载事实、哪些解析细节省略、各部分是否达到容量限制、进程/线程是否正常完成记录。工具链启动的事实也保留。不先增加工具/应用分类、不按包名隐藏数据、不仅通过提高默认上限缓解一个例子。

## 后续顺序与停止条件

1. **CI 的小幅节省与默认输出的正面事实**：两项可独立推进；前者减少不产生新信息的运行，后者让已有结果直接可用。它们不需要重构实验底座。
2. **观察预算的事实与明细分离**：这是已经出现的能力阻碍，优先于增加更多依赖查询功能。先定保留语义和资源约束，再实现一份有限方案。
3. **搜索目标与控制策略**：先明确用户需要的是可用规则还是逐次失败解释，再做小范围成本验证。不要直接删除恢复调用，不把“更便宜”与“证据完全相同”混为一谈。
4. **集中发布**：为已完成能力准备 0.13.0；按完成情况收口，不要求每个讨论方向先实现，也不为每次工程交付升版。

已有 [下一阶段计划](next-stage-plan.md) 的有限验证、材料复用和真实收益记录继续适用；本次调整其中“不按版本号排进度”为“轮次不升版，完整交付可以发布”。本次输出反馈本身已是有效需求，不必先等待新的独立读者才能修正。暂不引入 GUI、新后端、自研沙箱、逐依赖细粒度权限搜索或跨次执行缓存。

每项交付至少记录它解决的具体问题、得到的确定事实、仍影响当前判断的缺口和实际成本。若仅新增更多限制文字、重跑已知实验或增加选项却没有改善一个用户判断，就不算达到这里的目的。
