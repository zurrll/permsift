# 快照与独立工作区

旧实现每个 trial 用 fs.cp 完整复制冻结输入，包括 node_modules。现在 macOS 使用系统 `/bin/cp -cRpPN`：APFS 支持时共享未修改文件的数据块，实际写入才分配新数据；每轮仍有自己的目录和文件 inode。Linux 上文件模块使用 Node COPYFILE_FICLONE 优先复制，沙箱执行仍只支持 macOS。

不使用硬链接或直接共用可写依赖目录。普通原地写入、通过内部符号链接写入、chmod、删除整个 node_modules，都只能改变该轮的副本。快照仍被后端保护，后续恢复与最终验证重新从冻结输入创建工作区。

系统复制工具在不支持克隆的磁盘上会回退到普通复制。`evidence/*.json` 的 workspace_fork 记录 strategy、duration_ms 和回退说明；clone-preferred 表示请求克隆，不是对实际共享物理块数量的审计。超时、取消或复制错误中止本轮，并清理部分副本；不能改为在原项目执行。

这个修改降低重复写入完整文件内容的开销，仍需为大量小文件创建目录项。输入第一次冻结与哈希、每轮文件变化哈希、任务运行及清理也需要时间，不承诺全部实验按相同比例加速。

运行本机对照：

```sh
npm run build
node scripts/benchmark-forks.mjs
```

脚本生成 2,048 个模拟依赖文件及一个大文件，总逻辑大小 256 MiB，分别测三次旧普通复制和新工作区创建，轮换先后顺序。每次创建后执行原地写入和依赖目录删除，确认源输入不变。结果位于 `.permsift/fork-benchmark.json`；只衡量创建工作区，不衡量整轮实验，也不是实际项目或其他磁盘的性能保证。

2026-09-30 本机 macOS 15.8 / Node 24.21.0 的三次对照：普通复制 2,027 / 1,227 / 1,209 ms，克隆优先 347 / 300 / 302 ms；中位数 1,227 → 302 ms，约减少 75.4%。各轮修改和删除后的源内容检查全部通过。

测试覆盖文件内容、可执行位、独立 inode、相对内部符号链接、跨轮恢复、既有目标保护、嵌套目录拒绝和取消；实际沙箱测试继续验证全部任务与前后边界。

## v0.6 完整性补充

npm tarball 可包含 ._ 开头的普通文件。本机发现 macOS cp 在伴随文件存在时会跳过某些 ._ 项；v0.6 在原生克隆后做目录枚举，将缺失项目作为数据补齐，保留文件模式和独立性。补齐通常是少量字节复制，证据记录 preserved_dot_underscore_entries。取消、超时和复制错误仍清理半成品。此枚举有额外成本，早期 302 ms 结果仅代表 v0.5 当时实现。

安装后快照进一步核对各根内容、文件/目录模式和内部链接，来源和克隆不匹配时保持 unknown。相关 Apple 实现可见 [cp 源码](https://github.com/apple-oss-distributions/file_cmds/blob/main/cp/cp.c) 的 ._ 跳过逻辑；行为以本机测试为准。
